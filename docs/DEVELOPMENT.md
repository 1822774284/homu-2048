## 架构要点

- **规则与渲染分离**：`engine3d.js` 不碰 DOM；`moveDetailed()` 额外返回每个方块的 from/to 与是否合并，供动画使用
- **静态格 + 动态块**：27 个线框格固定不动，只有方块元素带位移动画（160ms），合并时两块滑到同格再合成一块弹出
- **相机（WebGL 版）**：位置按 `(yaw, pitch)` 球面摆放，`up` 由同一个 `(yaw, pitch)` 算出而不是固定 `(0,1,0)`——这是越过 ±90° 不翻转的前提；层号与坐标轴各自按屏幕空间摆正

## 已知问题

1. 数字印在六个面上，一个方块能看到三个“4”，侧面上还会露出半个数字；可考虑只印顶面
2. 4×4×4 已上：方块分段降到 12（1728 面/块），满盘约 11 万三角形、65 个 draw；再往上（5×5×5）就得先把方块换成低模或合并批次
3. 求解器已换成两段前瞻：200 步均值 2510、20/20 局出 256；400 步均值 5753、18/20 局出 512。还有余量，但再往上就得加第三段或改评估，收益递减
4. 平面版的求解器只是简单贪心，没有前瞻；`?bot` 在 2D 下大约 245 步就无路可走

## 调试

- **固定视角**：`index.html?yaw=0.62&pitch=-0.62&radius=10`，三个参数都可省，用于按角度复现
- **固定盘面**：`?seed=7` 用确定性随机序列，同一 seed 每次发牌一致
- **临时换模式**：`?limit=100`（`0` = 无限），不写存档，适合复现某个上限下的对局
- **看数值**：`?debug=1` 左下角实时显示 `yaw / pitch / radius` 与 `fps · draw · tris`
- **从新局开始**：`?fresh=1` 忽略已存的局面（照常覆盖存档）
- **求解器代打**：`?bot=1` 每 320ms 走一步；自动化截图可用 `?botms=160` 加速（间隔只影响速度，不影响选点）
- **直接看终局**：`?sim=200` 载入即让求解器同步走 200 步（无动画、不等定时器），适合截图与对离线结果；无头截图里 `?bot` 会挂死，扫描一律用 `?sim`
- **虚格外观**：`?ghostmode=solid`（默认，实心盒）/ `tray`（浅凹槽）/ `pads`（平地板）/ `line`（线框）/ `frame`（外层大立方）/ `hybrid`；浓度 `?ghost=0.07`（0 隐藏）
- **切维度**：`?dim=2d` 平面、`?dim=3d4` 4×4×4（`?dim=3d` 回 3×3×3）；不写的话记住上次的选择（`homu3d.dim.v1`）
- `?demo=` / `?bot=` / `?seed=` / `?sim=` 是一次性对局，既不读档也不写档，避免把调试局写进存档
- 无头截图（不弹窗，走 SwiftShader）：
  `msedge --headless=new --disable-gpu --enable-unsafe-swiftshader --window-size=900,900 --virtual-time-budget=4000 --screenshot=out.png "<file url>"`
- 交互回归（真按键、真点击、真拖动，不依赖虚拟时钟）：`node probe-cdp.mjs`，连 DevTools 协议逐项断言并打印 PASS/FAIL（当前 42 项）
- **切语言**：`?lang=zh` / `?lang=en` 强制；不带参数时按 `localStorage('homu2048.lang.v1')` → `navigator.language`（`zh*` 中文，其余英文）。带 `?lang=` 访问会把结果写进 localStorage，所以 probe 用 `?fresh=1&lang=zh` 钉住中文——无头浏览器的 `navigator.language` 是 `en-US`，不钉的话「标题是立方体」那几项会先挂
- 渲染统计：`?debug=1` 的 HUD 末位是累计 `renders`，静止时不再增长即为按需渲染生效；页面另暴露 `window.__homuApp.game().stats()`
- 改完 JS 必须 **Ctrl+F5** 强刷；自动化抓图要用全新的 `--user-data-dir`，否则会吃到旧脚本
- **每次改 JS 都要改 `index.html` 里的 `?v=` 版本号**（现在是 `20261118b`）。线上同事/朋友不会 Ctrl+F5，
  缓存里留着旧 game3d.js 时会出现“界面是新的、行为是旧的”这种鬼问题（真遇到过：方向键两个方向都显示「远」）

- **2026-11-17 空闲不渲染 + 平面滑动手势**
  - 渲染循环原来是“每帧无条件 draw”：站着不动，144Hz 屏也在每秒画 144 次、每次 11–37 个 draw。
    现在改成按需渲染——`dirty` 标记 + 动画期间每帧；相机动了（`applyCam`）、场面重建（`rebuild`）、
    窗口尺寸变化、从平面切回来，都会打一次脏标记。
  - 实测（`?debug=1`）：静止 0.7 秒内 `renders` 9 → 9（改之前这段时间会多出约 100 次）；
    按一次方向键后 9 → 21（动画期间恢复逐帧）。场景内容不受影响，截图与改前一致。
  - 踩到的坑：`dirty` / `requestRender` 一开始声明在第一次 `applyCam()` 之后，命中 `let` 的暂时性死区，
    整页直接白屏。把声明挪到 `apiRef` 之前解决——而这次是 `probe-cdp` 的“无未捕获错误”断言第一时间抓到的。
  - 平面版补上**滑动手势**：棋盘 `.b2` 单独接管指针（`pointer-events: auto` + `touch-action: none`，
    不挡住标题栏），按下到抬起位移超过 22px 就按主轴方向推一步。手机上 2D 从“完全不能玩”变成可玩。
  - `api.stats()` 与页面上的 `window.__homuApp` 是给自动化用的调试入口，不影响玩法。

- **2026-11-17 平面 2D 模式（左上角切换）＋ 顺带修掉三个老毛病**
  - 标题上方加 `2D 平面 / 3D 立方` 胶囊，选择存 `homu3d.dim.v1`，`?dim=` 可临时指定。
  - 平面版是一局独立对局：`engine2d.js`（4 方向、标准合并、13 项自检）+ `game2d.js`（DOM 棋盘、滑动 110ms、合并/生成弹出）。
    与立方版共用同一页的 HUD、回退、音效、模式药丸，但**存档 / 最高分 / 步数模式分开**（`save2d` / `best2d` / `mode2d`）。
  - 切到平面时 3D 失活：不渲染、不吃键盘；切回来不重建场景，局面还在。
    3D 专属部件（画布、坐标轴、六向按钮、轴徽章、视角复位）由 `body[data-dim="2d"]` 一并收起。
  - 平面默认**无限步**（4×4 一局本来就要走几百步），模式药丸照常可用。
  - 顺带修掉三处早就存在的问题：
    1. **模式药丸的高亮从来没生效**：`b.dataset.on = String(x === y)` 写出来是 `"true"`，而 CSS 要的是 `[data-on="1"]`。
       全新打开时“当前是 200 步”根本看不出来。现在写 `'1' / '0'`。
    2. **全新浏览器默认不是 200 而是无限**：`Number(localStorage.getItem(MODE_KEY))` 对 null 得 `0`，
       而 `0` 正好是“无限”这个合法模式，被当成了已存选择。现在先判 null。
    3. 同一条在平面版按同样方式判 null（默认 0，结果不变，但逻辑一致）。
  - 验证：`node probe-cdp.mjs`（DevTools 协议发真按键/真点击）30 项全 PASS——
    默认 3D、3D 键盘有效、切 2D、**2D 下画布已隐藏 / 按钮没被盖住**、2D 键盘有效、Ctrl+Z 回退、
    切回 3D 步数不被 2D 覆盖、结算遮罩下仍可切换、重载后记住维度。
    截图 `docs/ui-2d.png`、`docs/ui-2d-from-3d.png`（先在 3D 渲染过再切 2D）、`docs/ui-3d.png`。
  - **上线后立刻发现并修掉：切到 2D 就切不回 3D。**
    `#board2d` 是 `position: fixed; inset: 0; z-index: 1` 的全屏图层，而 `header` 没设 z-index（默认 auto，画在它下面），
    于是平面棋盘把左上角的维度与模式按钮全盖住了——3D 下这层是 `display:none`，所以只有“切过去之后”才点不动。
    修法：棋盘层 `pointer-events: none`（它本来就不需要点击），并把 `header` 提到 `z-index: 10`。
    后者顺带修了同类问题：局终结算遮罩（`z-index: 9`）以前也会挡住整条标题栏，局终后切不了维度。
  - **另一个：切到 2D 后还能看见 3D 的旧画面。**
    three.js 建画布时自己写了 `canvas.style.display = 'block'`（内联样式），
    样式表里的 `body[data-dim="2d"] > canvas { display: none }` 优先级不够，压不住内联值。
    结果切到平面后画布并没消失，只是停着最后一帧——透过半透明的平面棋盘面板露出来，就是“2D 里看得到 3D”。
    只有先在 3D 渲染过一帧、再切过去才看得见；直接 `?dim=2d` 打开的场合画布从没渲染，所以一直没暴露。
    修法：`setActive` 里直接改写 `renderer.domElement.style.display`（谁拥有画布谁负责显隐），CSS 那条加 `!important` 兜底。
  - **测试教训**：第一版回归用 `el.dispatchEvent(new PointerEvent('pointerdown'))`，它绕过了浏览器命中判定，
    所以“被上层元素挡住”这种 bug 完全测不出来，测试全绿而真人一点就废。
    现在 `probe-cdp.mjs` 一律用 `Input.dispatchMouseEvent` 打真实坐标，
    并额外用 `elementFromPoint` 断言“这个位置最上层就是它”、用 `getComputedStyle` 断言画布真的 `display:none`。
  - 已知：平面版的 `?bot` 只是简单贪心（约 245 步到 256 就死），没做前瞻，别拿它当强度基准。

- **2026-11-17 求解器两段前瞻（200 步均值 2364 → 2510，256 从 16/20 局到 20/20）**
  - 旧版是 1 层贪心：6 个方向各走一步、评估局面，取最高。评估函数本身不差，卡在“走完这一步之后，新块从哪冒出来”完全没算。
  - 先试了单独给发牌求期望（每个空格 × 2/4 各评估一次）：均值 2354，噪声内，没用。只取最坏情况 2456；2/4 都枚举 2476（成本翻倍，不划算）。
    真正有效的是**均值与最坏的折中**，2510，而且 20 局全部出 256——注意均值那版还有 1 局只到 128。
  - 现在的 `bestMove`：走一步 → 对每个空格假设长出一个 2 → 每个假设下把 6 个方向全算一遍取最优 → 对这个集合取「均值 + 最坏」/2。
  - 成本约 **1.6 ms/步**（约 970 次 `move + evaluate`）；`?bot` 每 320ms 一步，CPU 占用 0.5% 左右，远到不了掉帧。
  - 对照（20 种子 × 200 步，种子 1111…22220）：均值 2364 → **2510**，中位 2372 → **2580**；400 步均值 5490 → **5753**，512 从 15/20 局升到 18/20。
  - 留出集（另取 20 个种子 4099…81980）同向变化：2345 → 2478，256 从 14/20 到 20/20，不是只对这一组种子调参调出来的。
  - 新增 `bench-solver.mjs`：与页面共用同一份 `engine3d.js` / `solver3d.js`，固定种子离线复算，
    `node bench-solver.mjs 200 page`；`page` 是线上实现，另有 `plain / expecti / twoply / twoplyMin / twoply24 / twoplyBlend` 对照。
  - 页面回归：`?sim=200&limit=200&seed=1111` 截图（`docs/solver-199-end.png`）显示 SCORE 2580 / MAX 256，
    与离线逐局 `1111:2580/256` 完全一致——浏览器里跑的就是被评测的那份代码。
  - **坑**：`?bot=1` 在无头截图里会挂死。虚拟时间推到带 `setInterval` 的页面上时，定时器与 rAF 互相等待，
    `--virtual-time-budget` 永远到不了期，浏览器不退出、也不出图。扫描用 `?sim=N`：同步结算 N 步、不等定时器，正常运行。

- **2026-11-17 音效（新增 `audio.js`）**
  - 全部现场合成，零音频文件：振荡器 + 噪声 + 一个 0.45s 的卷积混响（衰减噪声当脉冲响应），
    走**小调五声**音阶，同一步里两三个合并音同时响也不打架。
  - 音高随块值上升：`merge(4)` ≈ 262Hz、`64` ≈ 440、`512` ≈ 659、`2048` ≈ 880（实测自相关）。
  - 声音清单：move（移动，无合并时的闷敲，约 120ms）/ merge（合并，约 300ms）/
    vanish（特殊块对消，三个上行短音）/ over（局终，两声下行 700ms）/ undo（回退，下滑）/ click。
  - **移动音改过一版**：初版是“1500→420Hz 噪声气流 + 940Hz 亮音”，舰长反馈难听——
    噪声像纸摩擦、亮音像电子表按键，两声叠一起更糟。现改为低频下坠的闷敲
    （215→138Hz + 一层薄泛音 + 只留 20ms 的起音嗒）。5 个候选留在 `sfx-lab.html` 里可换。
  - 电平实测：move 0.18、合并类 0.31、over 0.17、vanish 0.11，最大 0.33 不削顶；
    波形与数值见 `docs/audio-levels.png`。测试用 `OfflineAudioContext` 离线渲染，
    `HomuAudio.engine(ctx)` 与线上共用同一套合成代码。
  - 浏览器不许无手势出声：`AudioContext` 在第一次按键/点击时才创建并 resume。
  - 挂接点：`step()` 里滑动一次 + 每个合并按 `order` 错开 35ms；`spawn` 落地；`over` 局终；
    `undo()` 回退；按钮点击。**计数实测**：16 步 → slide 16 / spawn 16 / merge 7，Ctrl+Z → undo 1。
  - 开关：底部 `🔊` 按钮或 M 键，状态存 `homu3d.sound.v1`。
  - **踩过的坑**：静音时原本给按钮加 `.dim`，而 `.dim` 带 `pointer-events: none`（本来是给“回退没得退”用的），
    结果音响一关按钮就点不动、再也开不回来。现在音响用单独的 `.muted`（只降透明度，不拦点击）。
    教训：**表达“禁用”的样式别顺手复用到“只是状态变灰”的元素上**。

- **2026-11-16 拖到顶/底时视角突然翻转（已修）**：轨道相机原来固定 `up=(0,1,0)`，
  俯仰不设限。视线与 up 共线（pitch=±90°）时 `lookAt` 的 right 轴会反向，
  越过极点的一瞬间整幅画面转 180°，就是“到底角后直接变方向”。
  实测：pitch 每步 0.57° 扫过 ±π，旧写法相邻帧最大跳变 **180.0°**，新写法 **0.6°**；
  `|pitch| < 89°` 区间新旧朝向差异 **0.0000°**（常规视角一个像素都没动）。
  修法：up 跟着俯仰一起转，`up = R_y(yaw)·R_x(-pitch)·(0,1,0)`，
  即 `(-sinφ·sinθ, cosφ, -sinφ·cosθ)`，恒与视线垂直；越过极点变成连续翻滚而不是跳变。
  对照图：`docs/cam-pole-before-after.png`、`docs/cam-pole-sweep.png`。
